# SixSentences v0.2.0-alpha.3

This evaluation prerelease fixes container-provenance evidence validation.
Application behavior, database migrations and third-party dependency versions
are unchanged from alpha.2. Engine, API, web and extension release metadata move
together to a new immutable version; the macOS Companion remains source-only.

## What changed

- Accept BuildKit's exact SLSA v1 build-type URI and `buildDefinition` /
  `runDetails` structure, alongside the separately validated legacy SLSA v0.2
  form. Unknown URI prefixes and mixed schemas remain rejected.
- Preserve exact image-digest, OCI revision/version and runtime-receipt
  bindings. This is a format correction, not a relaxed security gate or a new
  claim that a provenance VCS hint independently proves source identity.

## Alpha.2 remains valid

The published alpha.2 source release and attested Python-engine artifacts remain
valid and unchanged. Its container builds, vulnerability scans and isolated
upgrade/restore drill passed, but the provenance validator rejected the real
BuildKit v1 metadata before image evidence could be attached. Existing alpha.2
image tags are not overwritten, and their presence in a registry is not a
substitute for published image-evidence receipts.

Alpha.3 requires its own source release checks and separately approved container
publication. Use prebuilt images only once this release includes `IMAGE_DIGESTS`,
SBOM/provenance, OCI identity records, `runtime-rehearsal.json` and
`IMAGE_SHA256SUMS`; then verify the checksums and select the digest references.
Only Linux amd64 and the explicit localhost web origin are covered. TLS-origin
web images must be operator-built. No existing release or image is replaced.

## Install and recovery boundaries

```console
git clone --branch v0.2.0-alpha.3 --depth 1 https://github.com/SixSentences/sixsentences.git
cd sixsentences
bash deploy/community/init-env.sh --local
docker compose --env-file .env.selfhost up --build --detach --wait
```

Read `deploy/community/README.md` and `deploy/community/BACKUP-RESTORE.md` before
accepting data. Existing operators must retain a verified backup and the newer,
independently held authenticated erasure journal before changing releases.
Registration and external processing still require operator configuration and
deployment-specific privacy/legal review; this release changes none of those gates.

The required upgrade drill uses the pinned alpha.1 API and the alpha.3 candidate,
not an exact-image alpha.2-to-alpha.3 upgrade. It applies the hash-bound,
single-Boolean-literal compatibility correction to alpha.1's original database
revision, then runs the unchanged prior API with a real synthetic corpus.
Candidate checks cover saved notes/files, post-backup erasure replay and a
separate fresh startup without a corpus. Snapshot rollback uses the pinned
alpha.1 API and the newer independent deletion journal. This is not evidence
that the original alpha.1 installer works unchanged, that schema downgrade is
safe, or that post-snapshot writes survive rollback. Only a successful runtime
receipt for these exact published digests proves that drill for this release.

No hosted billing, production data or credentials, new provider permissions,
signed/notarized native binaries, marketing site or new media are included.
The reviewed preview is unchanged. This remains alpha software; see `LICENSE`,
`THIRD_PARTY_NOTICES.md`, `TRADEMARKS.md` and `docs/RELEASING.md` for its boundaries.
